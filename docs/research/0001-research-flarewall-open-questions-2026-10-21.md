# Research: the open questions in plan 0001

This note answers the ten open questions in `docs/plans/0001-plan-flarewall-2026-10-21.md`. It is also the Phase 1 research note. Every source was read on 2026-10-21. A claim marked UNVERIFIED has no primary source yet.

## Recommendations

| # | Question | Pick | Choose the other option if |
|---|----------|------|----------------------------|
| 1 | Runtime | TypeScript on Node 22+, published as the npm package `flarewall`. TUI with Ink 8, loaded only by the `tui` command (section 11). | You want one static binary with no Node on the target. Then pick Go with Bubble Tea v2. |
| 2 | API layer | The official TypeScript SDK `cloudflare`, pinned to an exact 7.x version, plus one raw `fetch` for GraphQL | The `cf` CLI reaches a stable 1.0 and gets a GraphQL command. Then reconsider it as a backend. |
| 3 | Private data | One private GitHub repo: inventory YAML, backup JSON, and the scheduled workflow. Drift history lives in GitHub issues. | You need queries across runs, such as "zones that drifted 3 times in 90 days". Then add SQLite or D1 for drift history only. |
| 4 | Terraform | No. Keep Phases 2 to 4. | Issues #7128, #7381 and the Bot Management "inconsistent result" issues close. |
| 5 | Baseline shape | One baseline file for all zones. Each inventory entry sets parameters only, not rule overrides. | A zone needs a rule that no parameter can express. Then add named profiles, not free-form overrides. |
| 6 | Paid-plan zones | Apply the same Free-plan baseline. Check the zone plan, and never delete rules that flarewall does not own. | A paid zone needs a paid feature. Then add a plan-specific profile at that time. |
| 7 | Drift run location | A scheduled GitHub Actions workflow in the private data repo, with a read-only user API token | GitHub cron delays become a problem. Then use a Worker Cron Trigger on Workers Paid. |
| 8 | Alert channel | One GitHub issue per drifted zone. The run closes the issue when the zone is in sync again. | GitHub Mobile push is too slow for you. Then add a Telegram message when an issue opens or closes. |
| 9 | Open-source strip | Make every local choice a parameter with a neutral default, and add a CI check for private strings | Nothing. This step is necessary before the first public push. |
| 10 | Skill output | A branch and a pull request on the private data repo. CI posts the `flarewall diff` output on the pull request. | You run the skill with no network to GitHub. Then it writes a plain file edit. |

## Finding that changes a settled decision

The plan says "A token comes from the environment or from an existing Cloudflare login." The login part does not work for most of the baseline.

- The `wrangler` OAuth scopes include `zone:read`, but no firewall, zone settings, bot, or analytics scope (`packages/workers-auth/src/core/scopes.ts` in [workers-sdk](https://github.com/cloudflare/workers-sdk), main, 2026-10-21).
- The `cf` OAuth scopes add `dns_records:read/edit`, but also have no WAF, zone settings, bot, or analytics scope (`packages/workers-auth/src/cf/scopes.ts`, same repo).
- A login token can therefore list zones and DNS records only. Calls 3 to 6 in the table below need a custom API token.

Recommendation: change the decision to "A token comes from the `CLOUDFLARE_API_TOKEN` environment variable." Use two tokens: a read-only token for `status`, `diff`, and the scheduled run, and a write token for `apply` on the owner's machine.

## 1. Runtime

| Criterion | TypeScript on Node | TypeScript on Bun | Go |
|-----------|--------------------|-------------------|----|
| Cloudflare SDK | `cloudflare` 7.3.0 (2026-10-03), generated by Stainless | Same package; the README lists Bun 1.0+ | `cloudflare-go/v7` v7.13.1 (2026-10-20), generated by Stainless |
| Typed rule payloads | Yes (`BlockRule`, `ManagedChallengeRule`, `RedirectRule`) | Same | Yes |
| TUI | Ink 8.0.0 (React 19.3+, Node 22+), mature | OpenTUI 0.6.6, pre-1.0 | Bubble Tea v2.1.0 (2026-10-08), mature |
| Distribution | `npm i -g flarewall`; needs Node | Single binary for 8 targets | Single binary; an npm wrapper needs GoReleaser Pro or a hand-built esbuild-style wrapper |
| Baseline validation | Zod 4.6.7, with `z.toJSONSchema()` for editor support | Same | go-playground/validator, jsonschema/v6, CUE (pre-1.0) |
| Render tests | Vitest snapshots | `bun test` snapshots | Golden files in `testdata/` |
| Runs in a Worker | Yes | Yes, with a portable core | Only through WASM |

The two SDKs cover the same API, so the SDK does not decide the runtime. The TUI library and the npm name decide it. Ink is mature and native to Node. The npm name `flarewall` is free and only matters for a TypeScript build. The dev box already has Node and pnpm.

Keep the core free of Node-only APIs. A Worker can then run the core later.

## 2. API layer

One row per call that the baseline needs.

| Call | TS SDK v7.3.0 | Go SDK v7.13.1 | `cf` CLI 1.0.0-beta.20 | `wrangler` 4.151.3 | Terraform provider v5.28.1 |
|------|---------------|----------------|------------------------|--------------------|----------------------------|
| List zones in all accounts | `zones.list()`, paginated, filter by `account.id` | `Zones.List` | `cf zones list` (JSON array) | None | `cloudflare_zones` data source (UNVERIFIED) |
| List DNS records | `dns.records.list()` | `DNS.Records.List` | `cf dns records list --zone`, one page per call | None | `cloudflare_dns_records` data source (UNVERIFIED) |
| Get and update a phase entry point (`http_request_firewall_custom`, `http_ratelimit`, `http_request_dynamic_redirect`) | `rulesets.phases.get/update` | `Rulesets.Phases.Get/Update` | `cf rulesets entrypoint get/update` | None | `cloudflare_ruleset` (see section 4) |
| Get and set zone settings (`always_use_https`, `browser_check`) | `zones.settings.get/edit` | `Zones.Settings.Get/Edit` | `cf zones settings get/edit` | None | `cloudflare_zone_setting` |
| Get and set Bot Fight Mode | `botManagement.get/update` | `BotManagement.Get/Update` | `cf bot-management get/update` | None | `cloudflare_bot_management` |
| Read Security Events (GraphQL) | No wrapper; raw `fetch` to `/client/v4/graphql` | No wrapper | No command | None | None |

Auth model:

- TS and Go SDKs use an API token. One token can cover several accounts, so `zones.list` returns the zones of every account in the token.
- `cf` uses a device-code login (`--no-browser` works on a headless box), named profiles, and a `CLOUDFLARE_API_TOKEN` override. It does not reuse a `wrangler login`.
- `wrangler auth token --json` prints the stored token. The OAuth scopes are too narrow, as the finding above shows.

Stability:

- The TS SDK had three majors in ten months: v5.0.0 (2025-09-02), v6.0.0 (2026-04-30), v7.0.0 (2026-07-09). Its README allows some breaking changes in minor versions. Pin the exact version.
- The `cf` CLI is an open beta, launched 2026-09-28. It had 20 beta releases in about three weeks. The current script pins beta.12. In non-interactive mode, an aborted destructive command exits 0. That breaks the per-zone failure count in `apply`.
- `wrangler` has no zone security commands. It is not a candidate.

A gap that affects every layer: a PUT to a phase entry point can give the rules new IDs. Security Events then lose the link to the rule ([terraform-provider-cloudflare#6932](https://github.com/cloudflare/terraform-provider-cloudflare/issues/6932), open). flarewall must send each rule with a stable `ref`, and keep the existing `id` where it can. The current script already does this for redirect rules only. Phase 7 needs it for all rules.

Security Events on the Free plan: retention is 31 days, the largest query window is 30 days, and the quota is 300 GraphQL queries per 5 minutes. The `settings` node of the GraphQL API returns the real limits for a zone. The dataset name `firewallEventsAdaptive` comes from recall and is UNVERIFIED for 2026.

Evidence:

- `cf` launch and beta status → https://blog.cloudflare.com/cloudflare-cf-cli-launch/ (2026-09-28) and https://developers.cloudflare.com/cf/get-started/
- `cf` exit code 0 on an aborted command → https://developers.cloudflare.com/cf/ci/ (2026-10-21)
- `wrangler` commands → https://developers.cloudflare.com/workers/wrangler/commands/ (2026-10-21)
- TS SDK majors → https://github.com/cloudflare/cloudflare-typescript/releases
- Security Events retention → https://developers.cloudflare.com/waf/analytics/security-events/ (updated 2026-10-02)
- GraphQL limits → https://developers.cloudflare.com/analytics/graphql-api/limits/ (2026-10-02)

## 3. Private data store

| Option | Review and history | Drift-history query | Reachable from the dev box and the runner | Cost |
|--------|--------------------|---------------------|-------------------------------------------|------|
| Private GitHub repo | Git diff and pull request review | Weak (git log, issue search) | Yes, through git and `GITHUB_TOKEN` | Free |
| SQLite file | None | Strong | Only where the file is | Free |
| Postgres | None | Strong | Needs a hosted server | Paid or self-run |
| Cloudflare D1, R2, or KV | None | Strong (D1) | Needs a Cloudflare credential on the dev box, which the rules forbid | Free tier |

Recommended layout of the private repo:

- `inventory/<account>/<zone>.yaml`: zone ID, host roles, and the parameters from section 5.
- `backups/<zone>/<UTC time>/`: the two ruleset phases, the redirect phase, the zone settings, and Bot Management, as the current script writes them.
- `.github/workflows/drift.yml`: the scheduled run from section 7.
- Drift history: the GitHub issues from section 8.

The size of one backup is about 10 to 50 KB of JSON per zone. This number is an estimate and is UNVERIFIED. 50 zones then give about 2.5 MB per full apply, which git holds with no problem.

The tool reads the data repo path from a config value or an environment variable. The tool repo never holds the path or the data.

Evidence: D1 Free limits → https://developers.cloudflare.com/d1/platform/limits/ (2026-10-21)

## 4. Terraform as a replacement for Phases 2 to 4

Verdict: no. Open issues on the provider tracker on 2026-10-21:

- [#7128](https://github.com/cloudflare/terraform-provider-cloudflare/issues/7128): after an import, `skip` action parameters and `ratelimit.counting_expression` show drift on every plan. This hits both the custom phase and the rate limit phase.
- [#7381](https://github.com/cloudflare/terraform-provider-cloudflare/issues/7381): since v5.25.0, `plan` sends a dry-run PUT. A read-only token can no longer run a drift check.
- [#7334](https://github.com/cloudflare/terraform-provider-cloudflare/issues/7334): imported rulesets always drift.
- [#6727](https://github.com/cloudflare/terraform-provider-cloudflare/issues/6727), [#7385](https://github.com/cloudflare/terraform-provider-cloudflare/issues/7385), [#7411](https://github.com/cloudflare/terraform-provider-cloudflare/issues/7411): `cloudflare_bot_management` gives "inconsistent result after apply" from v5.14 to v5.27.
- [#5505](https://github.com/cloudflare/terraform-provider-cloudflare/issues/5505): the provider does not back off on HTTP 429.

`terraform plan -detailed-exitcode` returns 2 when it finds a diff ([docs](https://developer.hashicorp.com/terraform/cli/commands/plan)). With the perpetual diffs above, a daily run reports false drift. Terraform also needs a state file that holds every client zone, which is more private data to store.

The research settles this question, so the one-zone test in the plan is not necessary.

## 5. Baseline shape

This is a design question with no external source. The pick comes from the current script.

Recommendation: one baseline file, and one inventory entry per zone that sets parameters. The current script already has a fixed set of per-zone inputs:

```yaml
# inventory/<account>/example.com.yaml (private repo)
zone: example.com
zone_id: 0123abcd...
hosts:
  api: [api.example.com]
  wordpress: [blog.example.com]
geo:
  enabled: true
  country: XX
redirects: root        # root | www | https | skip
rate_limit:
  requests: 300        # optional; the baseline default applies when absent
```

Why parameters and not overrides:

- Drift has one meaning: the live zone differs from `render(baseline, inventory entry)`.
- A rule change in the baseline reaches every zone, which is the goal of the tool.
- The skill proposes an edit to a small, typed file. Zod rejects a bad value before `render` runs.

Bot Fight Mode and Browser Integrity Check stay derived from the host roles, as in the current script. They are not separate parameters.

## 6. Zones on a paid plan

This is a design question. Two facts from the current script decide it:

- `phases update` replaces every rule in the phase, so `apply` deletes a hand-made rule.
- The Free-plan baseline uses 3 or 4 of 5 custom rules and 1 rate limit rule. A paid plan allows more of both, so the Free baseline also fits a paid zone. The exact Pro limits are UNVERIFIED.

Recommendation:

1. Read `zone.plan` in `status` and show it in the row.
2. Give every flarewall rule a `ref` with a fixed prefix, such as `flarewall_`.
3. In `apply`, keep the rules that have no `flarewall_` ref, in their current order after the owned rules. This is the redirect-rule logic of the current script, applied to all phases.
4. In `diff`, report rules that flarewall does not own as "unowned", not as drift.
5. Check the Free-plan limits against the total count of owned and unowned rules before a write.

Item 3 also protects Free-plan zones from the loss of a hand-made rule. Do not add paid features such as the `matches` operator until a paid zone needs them.

## 7. Where the scheduled drift run lives

| Option | Fit for 50 zones | Secret storage | Cost | Risk |
|--------|------------------|----------------|------|------|
| GitHub Actions cron in the private data repo | Yes | Environment secret | About 60 of 2,000 free minutes per month | The cron can start late |
| Worker Cron Trigger, Workers Free | No: 50 subrequests per run | `wrangler secret` | Free | Fails at about 300 calls per run |
| Worker Cron Trigger, Workers Paid | Yes: 10,000 subrequests | `wrangler secret` | About $5 per month (UNVERIFIED) | A second deploy target |
| Dev box cron | Yes | Breaks the no-login rule | Free | No backups, the box can go down |

Call budget: 50 zones need about 5 to 6 calls each, so about 300 calls per run. The Cloudflare API limit is 1,200 requests per 5 minutes per user, shared by the dashboard, the API, and every token of that user. The run must back off on HTTP 429.

Token:

- A user API token can cover zones in several accounts.
- Use a user token, not an account-owned token. The docs mark Super Bot Fight Mode as not compatible with account-owned tokens, and an account-owned token belongs to one account.
- Permissions for the drift token: Zone Read, Zone Settings Read, Zone WAF Read, Bot Management Read, and a rulesets read permission. The exact permission for a zone-level phase GET is UNVERIFIED. One test call against one zone settles it.
- Analytics Read goes on the skill's token only.
- Set an expiry date on the token, and rotate it before that date.

The 60-day auto-disable of scheduled workflows is documented for public repos only. The behaviour for a private repo is UNVERIFIED. Each drift run that changes an issue does not count as repo activity for that rule, so watch the first 60 days.

- Schedule delays and the public-repo 60-day rule → https://docs.github.com/en/actions/writing-workflows/choosing-when-your-workflow-runs/events-that-trigger-workflows (2026-10-21)
- Actions minutes for private repos → https://docs.github.com/en/billing/managing-billing-for-your-products/managing-billing-for-github-actions/about-billing-for-github-actions (2026-10-21)
- Workers limits → https://developers.cloudflare.com/workers/platform/limits/ (updated 2026-10-12)
- API rate limit → https://developers.cloudflare.com/fundamentals/api/reference/limits/ (2026-10-21)

## 8. Alert channel

| Channel | Dedupe | Mobile push | Setup | Fit with GitHub Actions |
|---------|--------|-------------|-------|--------------------------|
| GitHub issue | One open issue per zone, closed on re-sync | GitHub Mobile (UNVERIFIED) | None; uses `GITHUB_TOKEN` | Direct |
| Telegram bot | You store state or edit a message | Yes | Bot token and chat ID | One HTTP POST |
| Email | Manual | Depends on the client | SMTP credential | Extra secret |

Cloudflare has no notification type for a ruleset change, a WAF rule change, or a zone setting change. "Security Events Alert" is for Business and Enterprise plans and reports traffic spikes, not config changes. flarewall must detect drift itself.

Recommendation:

- Open one issue per drifted zone, with the labels `drift` and the zone name, and the diff in the body.
- When the zone drifts again, update the open issue.
- When the zone is in sync, close the issue.
- Later, add the actor from Audit Logs v2 (18 months of history, Account Settings Read) to the issue body.

Evidence:

- Notification types → https://developers.cloudflare.com/notifications/notification-available/ (2026-10-21)
- Audit Logs v2 → https://developers.cloudflare.com/fundamentals/account/account-security/audit-logs/ (2026-10-21)
- Telegram Bot API → https://core.telegram.org/bots/api (2026-10-21)

## 10. How the skill writes its proposal

Recommendation: a branch and a pull request on the private data repo.

- The skill edits the baseline or an inventory file on a new branch and opens a pull request with `gh`.
- A workflow in the data repo runs `flarewall diff` with the read-only token and posts the output as a pull request comment.
- The owner merges the pull request, then runs `apply` on the owner's machine.
- The skill never holds the write token, so it cannot apply a change. This enforces the "never applies" rule with a token boundary, not only with an instruction.

Fallback: when the skill has no GitHub access, it writes the file edit in the working tree and prints the `diff` output.
